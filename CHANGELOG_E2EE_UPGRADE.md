# 🔐 Апгрейд E2EE и исправления — отчёт об изменениях

## Главная проблема, которая была исправлена

**Шифрование в исходном проекте не могло работать между двумя разными людьми.**

Ключ шифрования (`masterKey`) выводился из **собственного пароля отправителя**
(`CryptoUtils.deriveMasterKey(password, salt)`). Получатель сообщения не мог
его расшифровать в принципе — у него другой пароль, а значит другой ключ.
«Сквозное шифрование» существовало только на бумаге.

Дополнительно:
- При регистрации шифрование вообще не инициализировалось.
- В `initializeEncryption()` использовалась необъявленная переменная
  `userSalt` — при включённом `'use strict'` это должно было выбрасывать
  `ReferenceError`, который тихо проглатывался в `catch`.
- История переписки (`get_history`) отдавалась клиенту без полей
  `encryptedContent`/`encryptionHint` — при открытии старого чата вместо
  текста показывалась бы «сырая» base64-абракадабра, а расшифровка истории
  вообще не вызывалась в коде.
- В подтверждении отправки (эхо сообщения самому отправителю) терялись поля
  `encryptedContent`/`encryptionHint`/`isEncrypted` — собственное
  зашифрованное сообщение не могло быть расшифровано у самого отправителя.

## Новая архитектура: E2EE v2.0 (ECDH P-256 + HKDF + AES-256-GCM)

1. **Идентичность.** При первом входе на устройстве генерируется постоянная
   пара ключей ECDH (P-256). Приватный ключ хранится в IndexedDB как
   **non-extractable** `CryptoKey` — раскрыть его в виде байт нельзя даже
   через инъекцию кода в браузере. Публичный ключ публикуется на сервере.
2. **Личные чаты.** Ключ переписки — это ECDH shared secret между приватным
   ключом одного собеседника и публичным ключом другого. Он не передаётся по
   сети — оба участника независимо выводят один и тот же ключ.
3. **Групповые чаты.** Генерируется случайный 256-битный групповой секрет.
   Он «оборачивается» (шифруется) отдельно для каждого участника через ECDH
   с ним и сохраняется на сервере в таблице `group_key_shares`. Сервер
   хранит только шифротекст — прочитать групповой ключ он не может.
4. **Каждое сообщение** дополнительно шифруется уникальным ключом,
   выведенным через HKDF из ключа переписки + случайной соли — компрометация
   одного сообщения не раскрывает остальные (как и было в исходном дизайне,
   просто теперь исходный ключ — настоящий общий секрет, а не пароль).
5. **Сервер никогда не видит приватные ключи** и не может расшифровать
   переписку — он выполняет только роль "почты": хранит и раздаёт публичные
   ключи, обёрнутые групповые ключи и шифротекст сообщений.

### Известное ограничение
Ключевая пара привязана к конкретному браузеру/устройству — синхронизации
между устройствами нет. При входе с нового устройства будет сгенерирована
новая пара ключей, и старые сообщения, зашифрованные под старый ключ,
станут нечитаемы на новом устройстве. Это осознанный компромисс для базовой
версии; полноценная многодеустройственная синхронизация ключей (например, по
типу Signal's sealed sender / linked devices) — заметно более сложная фича,
которую стоит делать отдельным этапом.

## Что не тестировалось "живьём"

Я не разворачивал полный стек (Node.js + PostgreSQL + WebSocket + браузер)
в этой среде, поэтому синтаксис всех изменённых файлов проверен через
`node --check`, а логика — сквозным ручным прочтением всех точек
шифрования/расшифровки и сверкой протокола клиент↔сервер. Перед продакшен-
деплоем настоятельно рекомендуется:

1. Развернуть на staging-окружении (Railway/локально с PostgreSQL) и
   вручную проверить сценарии: регистрация → отправка личного сообщения
   между двумя новыми аккаунтами → перезагрузка страницы → чтение истории;
   создание группы из 2+ участников → сообщение в группе на каждом аккаунте.
2. Проверить откат: если у одного из участников нет публичного ключа
   (старый браузер без JS/IndexedDB), сообщение сейчас будет отправлено без
   шифрования — это by design (graceful degradation), но стоит решить,
   устраивает ли это ваш продукт, или лучше блокировать отправку.
3. Прогнать `npm audit` в `server/` и обновить зависимости.

## Прочие рекомендации из уже имевшегося отчёта `SECURITY.md`, которые остаются актуальными

- Заменить `rejectUnauthorized: false` для PostgreSQL SSL на настоящую
  проверку сертификата Railway (сейчас это MITM-риск на уровне БД).
- Добавить структурированное логирование security-событий (сейчас много
  `console.log` с деталями входа, включая куски хэшей — стоит убрать перед
  продакшеном).
- Рассмотреть rate-limit не только по IP, но и по логину/устройству.
